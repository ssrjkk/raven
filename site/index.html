Why Raven

Built for control

Your code, your keys, your infrastructure. No Raven-run service in the middle, no telemetry by default, no vendor lock-in.

Self-hosted

One Python process on your own server. Nothing of yours runs on anyone else's hardware: the calls it makes go to the LLM provider, the messengers and the tools you configure, and every one of those destinations is listed in the egress map.

66 tools

Files, shell, git, web search, code analysis, testing, memory, routines, monitors — all over MCP.

Two transports

stdio for local clients that spawn the server as a subprocess, JSON-RPC over HTTP for remote access.

Workspace confinement

Every file operation is bounded to your project. Symlinks resolved, escape attempts blocked.

Keyed auth

HTTP transport requires a secret token. Fail-closed: unconfigured means rejected, not accepted.

MIT licensed

Use it, modify it, distribute it. No copyleft, no strings attached.

Run it

One registry, three ways in

The same tools are reachable as an MCP server, as a terminal coding agent with its own session store, and behind a gateway that holds the channel adapters.

MCP server

Stdio for a client that spawns the process, JSON-RPC over HTTP for one that reaches it across a network.

stdio 
raven-mcp --workspace <dir>
ravencode-mcp --workspace <dir>

serverInfo.name · raven-mcp / ravencode

Coding agent

RavenCode runs the registry in an agent loop, keeps sessions on disk, exports them with credentials stripped and answers as an OpenAI-compatible endpoint.

cli 
ravencode tui <dir>
ravencode serve --port 8080
ravencode session export <id>

sessions under the data dir · basic auth on serve

Gateway

One process holds the registry, the DM policy and the messengers, so a chat message reaches the same tools a client frame does.

cli 
raven start
raven start --daemon
ravenflow

15 channel adapters · DM policy pairing|open|closed
