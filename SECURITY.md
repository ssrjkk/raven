### Проверка загрузки

Каждый тег публикует `Raven.exe` вместе с `Raven.exe.sha256` и attest-документом о сборке:

```bash
sha256sum --check Raven.exe.sha256     # Windows: certutil -hashfile Raven.exe SHA256
gh attestation verify Raven.exe --repo ssrjkk/raven
```

Контрольная сумма отвечает на вопрос «целый ли файл», attest — «из этого репозитория, из этого
коммита и этого запуска `Build EXE`». Ни то, ни другое не означает «безопасно запускать».

## Модель безопасности

### Политика доступа DM

По умолчанию Raven использует **парную** политику:
- Неизвестные отправители получают код привязки
- Бот не обрабатывает сообщение, пока код не подтверждён
- Подтверждение: `raven pairing approve <channel> <code>`

Доступные политики:
- `pairing` (по умолчанию) — код привязки для новых отправителей
- `open` — все сообщения обрабатываются (требуется настройка `allowFrom`)
- `closed` — только явно разрешённые отправители

### Безопасность выполнения инструментов

- **exec_security**: `deny` (по умолчанию), `ask` или `full` — относится к *exec-классу* инструментов:
  `shell`, `python`, `process_*`, `browser_*`, `mcp_*`, `node_*`, `chaos_*`, `db_query`, `http_post`,
  `email_send`, `git commit/push/pull/checkout`, `plugin_*`. При `deny` агент отказывает им всем —
  этот режим действительно проверяется в `Agent._execute_tool()`, а не только задокументирован
- **exec_ask_mode**: `off`, `on-miss` (по умолчанию — `always`). Подтверждение, которое некому
  запросить, — это **отказ**, а не разрешение: без `confirm_fn` инструмент блокируется с указанием
  причины. В CLI спрос идёт в терминал и отказывает, если терминала нет; из 15 адаптеров каналов
  спросить умеют только Telegram и Discord, остальные (включая webchat) отказывают
- **workspace_only**: `true` (по умолчанию) — ограничивает пути, но требует `WORKSPACE_PATH`; без
  него ограничивать нечем, и `raven doctor` об этом сообщает
- **роли инструментов**: `dangerous=True` и `allowed_roles` исполняет `ToolRegistry.call(role=…)`;
  вызов без субъекта получает наименьшие привилегии, пустой список ролей закрывает инструмент.
  Роль задачи указывает тот, кто её создал (веб-сессия, CLI = `admin`), а не планировщик
- **дообучение**: `finetune_add_conversation`, `finetune_add_code`, `finetune_dataset_clear`,
  `finetune_load_model` и `finetune_start_training` помечены `dangerous=True`, то есть доступны только
  роли `admin` (запуск обучения дополнительно требует подтверждения). Корпус — процесс-глобальный
  билдер: строка без `consented=true` в него не попадает, а каждая попавшая строка проходит
  PII/кредакшн-редакцию до токенизации. `raven doctor` показывает состояние `Finetune Tracking`
- **sandbox_mode**: `non-main` (по умолчанию) — изолированное выполнение
- **sandbox_backend**: `subprocess` (по умолчанию), `docker` или `none`
- **изменения политик** (`POST /api/tools/policy`) — только роль `admin`

Подробнее: [docs/security/overview.md](docs/security/overview.md), а все внешние адреса, куда
процесс может отправить данные, перечислены в [docs/security/egress.md](docs/security/egress.md).

### Видимость контекста

- `all` (по умолчанию) — полный контекст
- `allowlist` — только разрешённые домены
- `allowlist_quote` — разрешённые домены, цитаты как есть

### Ограничение запросов

- По умолчанию: 60 запросов в 60-секундное окно на IP
- Burst-множитель: 1.5×, после чего IP временно блокируется
- Заблокированные IP разблокируются через 2× окна

### Одноразовые учётные материалы

- Токен подтверждения e-mail хранится как SHA-256 от значения (`auth_email_tokens.token_hash`) и никогда
  не пишется в лог: прочтение базы или журнала не даёт готовый к использованию credential.
  Подтверждение — `POST /api/auth/verify-email`, значение не попадает в query строку, историю браузера
  и `Referer`. Токен действует 24 часа и гасится первым же успешным подтверждением.
- SMTP-транспорт не настроен — подтверждение остаётся ожидающим, и это сообщается в WARNING (без значения
  токена); молча «подтвердить» нельзя.
- `WEB_SECRET_KEY` при отсутствии значения генерируется и сохраняется в `data/web_secret_key` с правами `0600`.

### Сессии

- Bearer-сессии хранятся в `auth_sessions` как `sha256(token)`, а не открытым текстом: дамп базы
  не даёт годный к использованию токен. Срок — 24 часа; сессия переживает рестарт процесса.
- `POST /api/auth/logout` гасит одну сессию, logout-all — все сессии пользователя, деактивация
  пользователя — тоже все. Токен отключённого пользователя отклоняется сразу, даже в другом процессе.
- Access log uvicorn выключен: он печатает строку запроса целиком, а SSE- и WebSocket-клиенты
  передают токен как `?token=` — у них нет способа выставить заголовок `Authorization`.
  `request_id_middleware` пишет метод, очищенный путь, статус и длительность.

### CORS

`WEB_CORS_ORIGINS` разбирается при загрузке конфигурации, а не при первом запросе:

- `*` при включённых credentials (`WEB_CORS_ALLOW_CREDENTIALS=1`, по умолчанию) — приложение не стартует.
  На wildcard Starlette отвечает Origin вызывающей стороны, то есть `*` с credentials означает «любой сайт
  читает ответы авторизованного пользователя», а не «никто».
- Поддомен-wildcard (`https://*.example.com`) отклоняется всегда: он сравнивается буквально и не
  не совпадёт ни с чем — конфигурация, которая выглядит открытой, на деле закрыта.
- Публичный API: `WEB_CORS_ALLOW_CREDENTIALS=0` и `WEB_CORS_ORIGINS=*` — единственная конфигурация,
  где wildcard разрешён; `raven doctor` и `raven security audit` помечают её как открытую.

## Аудит безопасности

Запустите `raven security audit` для 23 стандартных и 8 глубоких проверок:
- Надёжность секретных ключей
- Конфигурация API-ключей
- Права доступа к файлам
- Конфигурация CORS
- Принудительный HTTPS
- Конфигурация sandbox
- Таймауты сессий
- Безопасность Docker
- Уязвимости зависимостей
