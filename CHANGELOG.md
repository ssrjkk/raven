### Fixed
- `ravencode` sessions did not actually resume: `SessionStore.load` and the TUI `/load` rebuilt an agent the runtime never adopted, so the next `/ask` started from an empty conversation. `ReActAgent.load_state` now publishes the loaded agent as the live one, the TUI holds one `_session_agent` across turns, and `Orchestrator.dispatch(..., agent=...)` runs the task on that agent instead of constructing a new one — consecutive `/ask` calls accumulate history, and `/load` plus `ravencode session resume <id>` continue it
- `/agent <name> <task>` ignored the two fields that make a custom agent an agent: `system_prompt` and the `tools`/`restricted_tools` policy. The prompt reaches the conversation now, and the policy becomes `PermissionManager` deny rules (an allowlist denies every registered tool outside it)
- Custom commands with an `agent:` field crashed the TUI: `AgentType(cmd.agent.upper())` passed a member name where the enum expects its lowercase value (`ValueError: 'DEBUGGER' is not a valid AgentType`). Roles are looked up by member name now, autonomous fallback intact
- `ravencode upgrade` ran `pip install --upgrade ravencode`, which is not the distribution this project publishes, and reported pip's error as if the upgrade itself failed. It installs `raven-agent`, and `--version` pins `raven-agent==<version>`
- `ravencode integrations github run --payload` treated the flag as raw JSON while its help text documents base64 — the value the CI template passes was unusable. Both `--payload` and `RAVENCODE_GITHUB_EVENT` are base64-decoded now, with a clean error instead of a traceback on malformed input
- `ravencode integrations github install` / `gitlab install` required an env token and then wrote nothing, only printing where a workflow file should live. They write `.github/workflows/ravencode.yml` and `.gitlab-ci-ravencode.yml` from the packaged templates, refuse to clobber an existing file without `--force`, and print the matching `include:` line for GitLab. The GitHub workflow itself was missing from the repository; it ships now with least-privilege `permissions`, a `/ravencode` comment guard and a concurrency group
- `docs/cli.md` gained the RavenCode reference the agent actually has: TUI slash commands, `serve` and its auth, `session`, `auth`, `models`, `upgrade`, `integrations`
- `POST /aios/agent/multi` answered a bad `agent_type` in the request body with an unhandled `ValueError` (HTTP 500) while its sibling `/aios/agent` returned a structured "Invalid agent type" answer. Enum conversion at that boundary now raises `400` with the valid values listed, before any sub-agent is dispatched
- Secrets Scan schedule (`gitleaks detect --full-history --all`) failed on three fake secrets in the long-deleted Go auth microservice (`services/auth/*.go`); `services/` is added to the `.gitleaks.toml` path allowlist alongside `tests/` — push/PR scans only diff, so only the full-history job saw them. Verified locally with gitleaks 8.24.3 over all 363 commits: no leaks

The runtime stage now explicitly upgrades the package from the Debian repo, where `10.46-1~deb13u3` is already available, so the fix no longer waits on the base image refresh
- `aios/api/bridge.py` fallback text search used `Path.rglob("*")`, which enumerates every entry before filtering out `.git`/`node_modules`/etc. — slow on large workspaces. Replaced with `ravencode.runtime.fs_walk.iter_files`, which prunes excluded trees during the walk
- `ravencode serve` streaming never let go of an abandoned run: when the client disconnected mid-stream, the `ReActAgent` task went on executing tools with nobody reading its queue, and whatever it later raised was reported as never retrieved. `_run_agent_stream` now holds the generator in `try/finally` that cancels the task, cancels it eagerly once the requested `max_tokens` budget is spent, and attaches a done-callback that consumes the outcome
- `max_tokens` in a `POST /v1/chat/completions` body was accepted and ignored — the completion was as long as the agent wanted it. It is enforced at the API boundary now (char budget `max_tokens × 4`, `finish_reason: "length"` when the answer is trimmed, usage counted from the trimmed text), and both `max_tokens` (1–200000) and `temperature` (0–2) are range-checked by the request model rather than reaching the agent as arbitrary numbers. Sampling itself stays provider-side in `ravencode.json`
- `ravencode tui <dir>` on a missing directory died with a `FileNotFoundError` traceback out of `os.chdir`; it prints `No such directory: <dir>` and exits 1
- A `check_all.py` stage that reached its subprocess cap raised `TimeoutExpired` through `_run`, so the whole run aborted with a traceback that named no stage. The kill is turned into a failed result (rc 124, `TIMED OUT after Ns (process killed)`) reported by the stage that hit it, and the full-suite cap goes 900 → 1800 s because the batch legitimately runs long under coverage tracing
- Four channel adapters marked Stable could not accept a real delivery: the webhook router verified only its own `X-Webhook-Signature` HMAC, so every payload GitHub, GitLab, LINE and Feishu actually signed was rejected with 403 — and `GITLAB_WEBHOOK_SECRET` existed in the config surface but was never read. Each route now checks the header its platform sends: `X-Hub-Signature-256` (hex HMAC of the raw body) for GitHub, `X-Gitlab-Token` for GitLab, `X-Line-Signature` (base64 HMAC) for LINE, and `X-Lark-Signature` for Feishu, which is a plain SHA-256 over `timestamp + nonce + encrypt key + body` rather than an HMAC. - `raven/channels/irc` never connected. Its loop passed a keyword the socket API does not take, the read path was dead code, and the port-6697 case still spoke plaintext. It now opens a TLS socket by default, joins its channels after the `001` welcome, and reconnects with backoff on a dropped server
- `raven/channels/matrix` started its HTTP client and then sat idle: nothing ever called `sync`, so messages already in a room were delivered to the gateway on first connect and never again. The adapter runs the long-poll loop itself (`GET /_matrix/client/v3/sync?timeout=30000`, token carried forward, errors retried) and normalizes each `m.room.message` it receives

### Security
- `ravencode serve --password` was parsed and discarded — the OpenAI-compatible server honored only `RAVENCODE_API_KEY`, so a "password-protected" endpoint bound to a public interface answered every request unauthenticated while exposing tools that run shell commands. Basic auth is implemented (`--username`/`--password`, `RAVENCODE_SERVER_USERNAME`/`RAVENCODE_SERVER_PASSWORD`), both credential kinds are compared with `hmac.compare_digest`, and `run_openai_server` refuses any non-loopback bind when neither is configured (loopback without credentials only warns)
- `ravencode session import <url>` fetched the URL with plain `httpx.get`, so a "share link" could address internal services. It goes through `raven.core.security.ssrf.safe_fetch_async`, the same guard the web tools use, and a loopback or private target is reported instead of fetched
- `ravencode auth login` / `auth logout` wrote `~/.config/ravencode/auth.json` with the process umask; provider keys are now stored with mode `0600`, the convention `raven.core.config` already follows
- `SlackChannel.verify_signature` now fails closed when `signing_secret` is not configured (previously returned `True`, accepting unsigned requests)
- Webhook signature verification fails closed across the board: generic, `slack/events`, WhatsApp and every `_verify_webhook_signature` consumer (Google Chat, Signal, Teams, Feishu, LINE, GitHub, GitLab, GitHub Actions, Allure) now reject unauthenticated requests when no signing secret (`WEB_SECRET_KEY` / `SLACK_SIGNING_SECRET`) is configured, instead of accepting them — previously any unauthenticated POST could reach the self-heal/QA actions
- `confine_path` resolves symlinks with `realpath` before the workspace check, so a link inside the workspace pointing outside can no longer escape the boundary
- `cryptography` floor raised to `>=50.0.0` (runtime `secrets` extra and `dev`). The old `dev` cap `<45.0` resolved to 44.0.3, which pip-audit reports 10 open advisories against (incl. PYSEC-2026-3552, fixed only in 50.0.0); 50.0.1 audits clean, its 70 crypto-dependent tests pass, and wheels exist for 3.11/3.12 on Windows and Linux
- CI `security` job is now a real gate. It audited the runner's own preinstalled packages — the project was never installed — and both steps ended in `|| true`, so a known vulnerability could not fail the build. It now installs `.[dev]`, audits exactly that freeze (`pip freeze --exclude-editable` + `pip-audit --strict --no-deps`) and fails on any finding
- Exception text no longer reaches HTTP response bodies (the four `py/stack-trace-exposure` CodeQL findings). `ravencode.runtime.tools.execute_tool_public` is the boundary variant of `execute_tool`: it returns a fixed `[execution_error] tool failed` instead of the handler's message, and every path that writes a tool result into a response now uses it — both MCP HTTP routers, both MCP stdio servers and the RavenFlow `POST /api/tools/{name}` route. The agent loop keeps `execute_tool`, whose detail the model needs to repair a failing call. `admin_api` `check_now` returns `{"ok": true, "triggered": bool}` rather than the alert text it collected
- The `ravencode` MCP HTTP router had no authentication at all on `/mcp/rpc`, `/mcp/tools` and `/mcp/tools/{name}`. Auth now lives in one place, `raven.core.mcp/auth.py::authorize_request` (Bearer token or `X-Raven-Key`, token manager first, constant-time secret compare), shared by both routers; the duplicated per-router checks are gone
- A session id was a path component nobody validated. RavenFlow session ids arrive from HTTP bodies, WebSocket frames and files already on disk, and `raven/gateway/session_store.py` built filenames straight from them, so `session_id: "../../somewhere"` wrote or deleted JSON outside the sessions directory. The rule `^[A-Za-z0-9_-]{1,128}$` now lives in one function, `ravencode.runtime.session.validate_session_id`, and runs at every boundary: `POST /api/agent` (400) and `WS /ws` (error frame), `_get_or_create_session`, `SessionStore.save`/`remove`/`_path`, and `FlowSession.from_dict`, which skips a hostile or corrupt persisted file instead of loading it. `ravencode session delete|export|import` validates the argument and the imported payload's own `id`, and `aios/api/bridge.py` uses the shared validator in place of its local copy of the regex
- WhatsApp reused one secret for two jobs: `WEB_SECRET_KEY` both signed the inbound POST and answered the `hub.verify_token` handshake, so the key that guards the console and the gateway was the value an operator pastes into a Meta dashboard and then replays in a URL query string. `WHATSAPP_APP_SECRET` verifies the POST and `WHATSAPP_VERIFY_TOKEN` the handshake; each falls back to `WEB_SECRET_KEY` only when unset, and the same split is documented in `.env.example` and `docs/configuration.md`
- `ravencode session export --sanitize` masked only three exact key names at the top level of a dict, so live credentials survived inside header dicts, lists, non-string values and message text. It matches key *shapes* now (`api_key`/`apikey`/`api-keys`, `token`, `password`, `authorization`, `credentials`, `private_key`, `secret` — separators required, so `tokenizer`, `monkey` and `keyboard` stay intact), recurses into lists, and masks secret *values* wherever they appear: `sk-`/`sk-ant-`, `ghp_`/`github_pat_`, `AIza`, `xoxb-`, `AKIA`, `npm_`, `Bearer <token>` and PEM private-key headers
